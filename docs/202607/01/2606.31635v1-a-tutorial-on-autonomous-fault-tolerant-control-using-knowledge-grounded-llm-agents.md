## 摘要
过程工厂中的故障恢复仍然严重依赖操作员，尤其是当故障超出预定义的监督逻辑时。操作员需要解读警报、操作规程、管道和仪表图（P&IDs）、联锁以及工艺趋势，然后决定如何将工厂转移到安全操作模式而避免停产。本文探讨了大型语言模型（LLM）代理如何支持此类恢复决策。所提出的框架将LLM视为一个受约束的监督规划器。它利用工厂特定知识来提出恢复动作，并且每个提议在执行前都要经过外部验证器（基于符号或仿真）的检查。本文针对应用该框架设计了三个维度：LLM代理有用的恢复模式、区分可接受与不可接受提议的验证策略，以及由延迟、知识工程、安全集成和模型生命周期管理所施加的部署约束。为使该框架直接可用，我们提供了两个公开可执行的Python环境。这两个环境重新实现了已建立的案例研究，即一个模块化混合模块和一个连续搅拌釜式反应器，并通过可配置的故障以及用于自定义恢复和验证方法的定义接口进行了扩展。

## Abstract
Fault recovery in process plants still relies heavily on plant operators, especially when faults fall outside predefined supervisory logic. Operators interpret alarms, procedures, P\&IDs, interlocks, and process trends, then decide how to move the plant to a safe operating mode without triggering a shutdown. This paper examines how Large Language Model (LLM) agents can support such recovery decisions. The proposed framework treats the LLM as a constrained supervisory planner. It uses plant-specific knowledge to propose recovery actions, and every proposal is checked by an external validator (symbolic or simulation-based) before actuation. The paper develops three design dimensions for applying the framework: the recovery patterns for which LLM agents are useful, the validation strategies that separate admissible from inadmissible proposals, and the deployment constraints imposed by latency, knowledge engineering, safety integration, and model lifecycle management. To make the framework directly usable, two openly available executable Python environments are provided. Both re-implement established case studies, a modular mixing module and a continuous stirred-tank reactor, extended with configurable faults and defined interfaces for custom recovery and validation methods.

- **研究动机**：大型语言模型（LLM）能够推理文本描述、结构化元数据和操作员类的解释，可生成候选恢复动作。但LLM的随机性使其不适合直接作为控制器（可能产生幻觉、不可行动作）。因此，需要将经典FTC方法与LLM结合，形成可测试、可复用的框架。
- **整体含义**：论文提出一种以LLM为受约束监督规划器的框架，通过知识图谱和数字孪生支撑，并用外部验证器确保动作安全，为工业容错控制提供了新的范式。

## 2. 论文提出的方法论：核心思想、关键技术细节
### 2.1 核心思想
- **LLM作为受约束的监督规划器**：LLM不直接执行控制，而是基于工厂知识生成候选恢复动作，每个动作必须经过外部验证器（符号或仿真）检查后方可执行。
- **多代理工作流**：将操作员职责分解为监控、规划、动作合成、仿真、验证和重新提示（reprompting），由工具层支持（知识图谱提供上下文，数字孪生评估动态行为）。
- **底层控制保持不变**：常规的调节回路（如PID）继续运行，LLM仅负责高层监督重构。

### 2.2 关键技术细节
- **公式化流程**：
  - 提示构造：  
    `pt = Φ(xt, ft, R(K, xt, ft), ht)`，其中`xt`为状态，`ft`为故障上下文，`K`为知识图谱，`R`为检索函数，`ht`为历史验证反馈。
  - LLM生成候选动作：  
    `â_t ∼ πθ(·|pt)`，`â_t ∈ A`，`A`为可允许的监督动作空间。
  - 外部验证器评估：  
    `zt = V(xt, â_t, K, M)`，其中`M`为确定性模型或数字孪生。仅当`zt = accept`时动作才被应用；否则将失败原因追加到`ht`并重新提示，直至达到预算，然后切换到工程安全回退。

- **三个设计维度**：
  - **维度1 – 恢复模式（应用模式）**：
    - 模式A（离散监督路由）：有限状态机，动作空间组合但小，验证器为符号（廉价、多次提示）。
    - 模式B（连续设定点适应）：连续但有限区间和离散增量，验证器为仿真（昂贵、少提示）。
    - 模式C（混合恢复）：分阶段，符号+仿真验证。
  - **维度2 – 验证策略**：
    - 符号验证器检查结构可达性、执行器存在性，速度快但忽略动态可行性。
    - 仿真验证器用数字孪生滚动仿真，检查不稳定暴露、执行器饱和等，更全面但成本高。
    - 时间维度：动作执行前验证，动作展开时添加运行时监控。
    - 成本-延迟曲线：符号验证允许多次重新提示；仿真验证需限制预算，依靠高质量反馈（指明哪个包线被违反）。
  - **维度3 – 部署考虑**：
    - 计算与延迟：云LLM延迟高、信息暴露；边缘/本地模型推理能力弱但延迟低。需根据工艺动态选择。
    - 知识工程工作：构建知识图谱是主要部署成本，但模式可复用，实例数据需人工审核。
    - 安全集成：LLM永无执行权限，所有动作记录决策追溯，IT/OT边界需明确防止提示注入。
    - 模型生命周期：固定模型标识，用回归测试套件验证，结构化输出模式视为稳定契约。
