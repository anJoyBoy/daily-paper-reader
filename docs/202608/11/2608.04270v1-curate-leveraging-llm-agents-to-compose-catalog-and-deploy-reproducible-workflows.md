## 摘要
基于智能体的代码生成已显示出利用大型语言模型（LLM）生成、测试和部署代码来自动化和加速软件开发的潜力。对于工程师和科学家而言，此类系统有可能加速应用型与科学工作流的开发，同时降低在尚未充分受益领域的入门门槛。然而，一个关键差距仍然存在：现有的编码智能体主要关注代码生成，并未涵盖整个工作流生命周期，包括部署与共享。因此，用户需要自行开发并拼接模块，同时自行管理部署。为弥补这一差距，我们提出CURATE——组合、用户参与、复用与自动化任务执行——一种新颖的人机协同多智能体系统，利用LLM智能体在整个生命周期中管理和开发可组合工作流。该系统的一个关键特性是编目系统，允许跨工作流存储和复用模块。模块编目提供了一个基础，可通过促进精选模块和子图的共享与复用来扩展以支持FAIR原则。我们通过一个使用Claude Opus 4.8的初始原型证明了系统的可行性，包含6项实验：复现并改编源自SeBS-Flow基准套件的4个工作流，以及自动化开发并扩展一个利用环境工程中用于模拟厌氧消化的复杂机理模型的工作流。

## Abstract
Agentic code generation has shown promise in automating and accelerating software development by utilizing Large Language Models (LLMs) to generate, test, and deploy code. For engineers and scientists, such systems have the potential to accelerate the development of applied and scientific workflows while reducing barriers to entry in domains that have yet to fully realize their benefits. However, a key gap remains: existing coding agents primarily focus on code generation and do not address the entire workflow lifecycle, including deployment and sharing. As a result, users develop and stitch modules independently while managing deployment on their own. To address this gap, we propose CURATE - Composition, User-in-the-loop, Reuse, and Automated Task Execution - a novel human-in-the-loop multi-agent system that uses LLM agents to manage and develop composable workflows across their entire lifecycle. A key feature of the system is a catalog that allows for the storage and reuse of modules across workflows. Module catalogs provide a foundation that can be expanded to support FAIR principles by facilitating the sharing and reuse of curated modules and subgraphs. We demonstrate the feasibility of our system with an initial prototype using Claude Opus 4.8, comprising 6 experiments: reproducing and adapting 4 workflows derived from the SeBS-Flow benchmark suite, and automating the development and scaling of a workflow that leverages a complex mechanistic model in environmental engineering used to simulate anaerobic digestion.

- **背景缺口**：现有编码智能体（如Claude Code、Codex）虽能生成、测试和部署代码，但主要聚焦于代码生成本身，并未覆盖科学工作流的**完整生命周期**——包括组合、部署、监控、共享与复用。
- **用户痛点**：科研人员构建工作流需熟悉工作流管理系统（WMS）、手动编写各步骤代码、自行管理部署基础设施，学习成本高且耗时。

## 2. 方法论：核心思想、关键技术细节

### 核心思想
- 提出 **CURATE**（Composition, User-in-the-loop, Reuse, Automated Task Execution）：一个**人机协同（HITL）多智能体系统**，覆盖工作流全生命周期管理。
- 核心创新在于 **模块编目（Catalog）机制**：支持已验证模块的存储、检索、跨工作流复用与共享，为FAIR原则奠定基础。

### 系统架构：4个智能体
| 智能体 | 职责 |
|---|---|
| **WCA**（工作流组合智能体） | 根据用户自然语言草图生成高层工作流骨架（DAG），负责任务分解、优先级排序，并在门控处征求用户反馈 |
| **MCA**（模块候选智能体） | 执行**源解析**：为骨架中每个节点确定模块来源（目录复用/用户提供/前次修订/新生成），用BM25检索目录并判断是否需适配 |
| **MGA**（模块生成智能体） | 基于Claude Agent SDK实现或适配模块，拓扑排序后逐个生成函数，在本地scratch目录用FaaSr存根进行测试验证 |
| **WDA**（工作流部署智能体） | 部署工作流到目标基础设施并持续监控；运行后生成聊天机器人，支持用户问答、日志查看、修订建议等 |

### 关键流程
- 工作流生成遵循 **sketch → reify → test → deploy** 阶段，通过**9阶段LangGraph流水线 + 5个HITL门控（Gate 1-5）** 实现：
  - Gate 1（骨架）、Gate 2（候选解析）、Gate 3（代码审查）、Gate 4（部署确认）、Gate 5（运行后反馈/修订）
- **修订机制**：LLM判定用户修改请求属于“结构性变更”（修改DAG，回退到骨架阶段）还是“功能性变更”（修改已有函数，回退到解析阶段）。
- **资源隔离**：架构上推荐沙箱化执行（如容器），原型选择FaaSr（serverless FaaS WMS），利用容器化部署隔离模块。

## 6. 主要结论与发现

1. **可行性验证成功**：CURATE能够从自然语言提示出发，端到端生成、部署并验证科学工作流，包含代码生成、模块复用和HITL反馈修订。
2. **显著优于单智能体baseline**：基线在多次运行中表现出明显的输出不确定性，常产生运行时错误（如FaaSr动作名映射错误、S3参数名误用），需要人工修正；CURATE则通过结构化流水线和HITL门控避免此类问题。
3. **目录复用有效降低开销**：从E5到E6，在工作流复杂度提升（20路并发）的情况下，Token消耗近乎减半，且预处理流程无需重新验证，体现复用的实际收益。
4. **多智能体集成价值突出**：E6中WDA在部署后成功发现PyADM1模型参数硬编码问题（q_ad），主动提出修订建议并经用户确认后回环到组合/解析阶段，展现自动化部署监控+智能反馈的闭环价值。
5. **真实场景潜力大**：ADM1工作流的自动化有望为环境工程领域节省大量人工工时（论文估计每个机理模型校准可节省>100工程师小时）。

## 7. 优点

- **全生命周期覆盖**：不同于现有编码智能体只关注代码生成，CURATE打通了组合→部署→监控→修订→复用的完整闭环。
- **模块目录+BM25检索**：简洁有效实现模块级复用与共享，为FAIR原则落地提供了可操作的基础设施。
- **精妙的人机协同设计**：5个门控点实现分层验证，既保留用户控制力又不过度打断流程；结构性vs功能性修订的自动分类降低了用户负担。
- **拓扑排序驱动的生成策略**：MGA按依赖顺序逐个生成函数，上游函数或其输出可为下游提供真实数据上下文，提高生成质量。
- **目录+子图复用**：E4验证了从目录中整图复用（Split/Mao/Shuffle/Reduce）并附加新模块的可行性，展示子图级复用能力。
- **跨平台部署设计**：借助FaaSr实现多平台（Lambda、OpenWhisk、SLURM、GCP、K8s）适配，降低系统锁定风险。

## 8. 不足与局限

- **实验覆盖有限**：SeBS-Flow本质是性能基准而非科学工作流套件，其“科学”代表性有限；ADM1实验仅限于初始数据准备阶段，尚未覆盖完整端到端流程（质量平衡、特征工程、敏感性分析等）。
- **单次运行方差未评估**：除RF精度外，未对生成工作流进行多次运行统计分析；MGA代码生成的随机性（尤其在无种子情况下）可能引入结果波动，实验未系统评估。
- **baseline比较公平性存疑**：3次运行中“手动修正错误后再比较”的做法虽注明是修正“无法从给定上下文合理获知”的问题，但仍可能对baseline有利或有偏，需更多样本和更系统化的比较协议。
- **单一模型与WMS依赖**：仅在Claude Opus 4.8上验证，虽声明架构可扩展至其他模型，但未实证；FaaSr本身文档错误也暴露了目标平台成熟度问题。

- **Token成本不确定**：多智能体系统在部分实验中Token消耗高于baseline（需更多数据判断整体经济性），论文也承认需要更多实验评估。
