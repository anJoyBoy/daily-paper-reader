## 摘要
自动化机器学习（AutoML）系统在预先指定的预处理算子、学习器和超参数空间内搜索流水线：它们可以选择和调整已知组件，但无法在该空间之外产生结构。我们提出了LACE，一个AutoML框架，它转而搜索完整的可执行流水线程序：一个进化循环维护一个由scikit-learn兼容的Python类组成的种群，大型语言模型作为变异算子。据我们所知，LACE是第一个以这种方式构建通用表格流水线AutoML的框架，并在标准化OpenML任务上、在泄漏受控的协议下进行评估，该协议对生成器隐藏数据集身份。由于每个候选都是普通的Python代码，返回的流水线和产生它的搜索过程可以直接检查和编辑，而不仅仅是通过框架的模型对象。在68个OpenML分类任务上，带有GPT-5.4-mini的LACE显著优于auto-sklearn、H2O和固定的XGBoost基线，与所评估的最强基于搜索的系统AutoGluon相比没有可检测到的差异，同时覆盖了整个基准。较新的表格基础模型在其支持的任务子集上更准确，但应用固定的预训练预测器，而不是返回可编辑的特定于任务的程序。因此，LACE的贡献不在于原始精度，而在于由代码定义的搜索空间：完整的覆盖范围、从业者可以直接复用的流水线，以及通过编辑提示而非框架来扩展的组件集。

## Abstract
Automated machine learning (AutoML) systems search for pipelines within a space of preprocessing operators, learners, and hyper-parameters specified in advance: they can select and tune known components, but cannot produce structure outside that space. We present LACE, an AutoML framework that instead searches over complete executable pipeline programs: an evolutionary loop maintains a population of scikit-learn-compatible Python classes, and a large language model acts as the variation operator. To our knowledge, LACE is the first to formulate general tabular pipeline AutoML this way, evaluated on standardized OpenML tasks under a leakage-controlled protocol that withholds dataset identity from the generator. Because every candidate is ordinary Python, the returned pipeline and the search that produced it can be inspected and edited directly, rather than only through a framework's model objects. On 68 OpenML classification tasks, LACE with GPT-5.4-mini significantly outperforms auto-sklearn, H2O, and a fixed XGBoost baseline, with no detectable difference against AutoGluon, the strongest search-based system evaluated, while covering the full benchmark. Newer tabular foundation models are more accurate on the subset of tasks they support, but apply a fixed pretrained predictor rather than returning an editable task-specific program. LACE's contribution is therefore not raw accuracy but a search space defined by code: complete coverage, pipelines practitioners can reuse directly, and a component set extended by editing the prompt rather than the framework.

- **约束与审计**：
  - 提示词限制使用 scikit-learn、NumPy、SciPy、pandas；最多 3 个基学习器的集成；单一共享预处理；禁止内部 HPO/CV。
  - 这些约束仅通过提示要求而非硬性强制，执行器会尝试运行所有程序，事后用静态分析审计合规性。

## 3. 实验设计

- **数据集与基准**：
  - 使用 OpenML `amlb-classification-all` 基准套件中的全部 68 个分类任务；
  - 任务规模跨度大：样本数从 100 到 4,898,431，特征数从 4 到 10,000；
  - 67 个任务使用分类准确率，1 个任务使用 ROC-AUC。
- **评估协议**：
  - 使用 OpenML 预定义的十折划分；每折训练集再分出 20% 作为内验证；
  - 每个配置独立运行 5 次重复（种子 0–4），共用同一组预定义折；
  - LACE 在搜索中只使用内验证分数，最终选择后只在官方测试折上评分一次。
- **对比方法**：
  - 搜索式 AutoML 基线：AutoGluon-Tabular、auto-sklearn、H2O AutoML；
  - 固定非 AutoML 基线：XGBoost；
  - 表格基础模型：TabPFN v2.5、TabPFN v3、TabICL；
  - 为隔离搜索差异，LACE 与搜索式基线均限制为经典非神经表格学习器；基础模型单独评估。
- **LLM 骨干**：
  - GPT-5.4-mini（API）、DeepSeek-V4-Flash（API）、Qwen3-Coder-Next（本地 4-bit 量化）。
- **时间预算匹配**：
  - 每个基线获得与对应 LACE 任务重复相同的墙钟时间预算；
  - 单个候选超时上限：重任务 4 小时，普通任务 1 小时。
- **汇总指标**：
  - 每种方法按任务得分线性归一化为“归一化偏差”，并报告任务级平均秩、归一化接近度、覆盖率和逐对 Wilcoxon 检验（Holm 校正）。

## 4. 资源与算力

- 论文没有给出 GPU 型号、数量或硬件归一化的 FLOPs 数据；所有实验运行在一个**共享的异构计算集群**上。
- 每个候选评估受墙钟限制：普通任务 1 小时、重任务 4 小时（重任务按样本数≥40 万、特征数≥1000 或 样本×特征≥10^7 判定，共 20 个任务）。
- 整个实验规模：68 任务 × 5 重复 × 3 骨干 = 1,020 次完整运行，对应约 102,000 次计划候选评估（日志记录 101,959 个候选）。
- 单个 LACE 任务重复的平均墙钟时间从约 0.7 小时到超过 240 小时不等（如表 17 所示），表明该研究计算开销很大。
- 由于基础设施异构，作者明确表示这是“共同基础设施下的比较”，而非严格计算平价基准。

## 5. 实验数量与充分性

- **实验规模**：
  - 68 个分类任务 × 5 次重复 × 3 个 LLM 骨干，共 1,020 次运行；
  - 有效候选共 70,998 个（占记录的 69.6%），其中 GPT-5.4-mini 的有效率最高（87.3%），Qwen3 最低（46.8%）；
  - 最终 pipeline 共 1,020 个，全部可追溯。
- **消融与辅助实验**：
  - 配置消融：交叉率、后代数、父本选择、变异指令集；
  - 骨干筛选：先在 3 个任务上筛了 7 个 LLM，选出 3 个进入主实验；
  - 零样本对比：将每个运行的第一个候选与最终返回 pipeline 比较（内验证与官方式测试重放）；
  - 基础模型提示消融：安装但不提及 TabPFN vs 在提示中显式宣布 TabPFN，观察生成空间变化；
  - 合规审计：对所有 1,020 个最终程序做静态检测并人工复核。
- **充分性与公平性**：
  - 采用相同 OpenML 分割与任务指标，所有方法获得相同墙钟预算，使用 Holm 校正的配对检验，整体设计较为客观；
  - 但实验只覆盖单一基准套件（表格分类）、5 次重复、异构集群；审计是静态分析而非穷举；粗粒度摘要也不能完全消除预训练数据污染风险。

## 6. 论文的主要结论与发现

- **主结果**：
  - 在 45 个全部方法均完成的任务上，LACE(GPT-5.4-mini) 的平均任务级秩为 4.71，显著优于 auto-sklearn、XGBoost 和 H2O（Holm 校正 p<0.01）；
  - 与 AutoGluon 无显著差异（68 个共享任务中 33 胜 35 负，中位差 −0.001，p=0.66）；
  - 明显弱于 TabPFN v3 和 TabICL（但中位差距只有约 0.3 个百分点，且平均差对阵 TabICL 略优 +0.22）。
- **覆盖优势**：
  - LACE 所有变体都覆盖全部 68 个任务，而 TabPFN v2.5 仅覆盖 45 个、TabPFN v3 覆盖 62 个、TabICL 覆盖 67 个；
  - 在失败感知分析（68 任务）中，LACE(GPT) 平均秩 4.50，与 AutoGluon 4.59 基本并列，TabPFN v2.5 因缺失任务落到 6.10。
- **进化搜索确实有效**：
  - 首个候选可执行率：GPT 为 79.7%、DeepSeek 66.5%、Qwen3 37.6%，但最终 pipeline 全部有效；
  - 对有效首程序做官方式测试重放后，最终 pipeline 在 190/193 个骨干-任务单元上更好（中位提升 2.99 个百分点；Wilcoxon p<10^-32）。
- **生成结构多样且可编辑**：
  - 99.9% 的最终 pipeline 添加了额外预处理，73.3% 组合了至少两个学习器；

73.3% 组合了至少两个学习器；84.8% 暴露了至少一个可调超参数；部分程序使用了非典型但合法的组件（如自定义特征选择逻辑、条件化预处理分支、手动类别编码），这些在传统固定搜索空间中几乎不可能出现。
- **LLM 骨干影响显著**：
  - 三个骨干在相同任务上的最优结果分布差异明显，GPT-5.4-mini 整体最强，DeepSeek 次之，Qwen3 最弱（无效候选最多、秩最低）；
  - 提示词中显式声明“可用 TabPFN”会诱导模型偏向使用该组件，但零样本安装提示（不提及 TabPFN 名称）时模型也能自发生成类似的分层集成结构，说明模型具有一定的组件感知与迁移能力。

## 7. 论文的主要局限与潜在问题

- **计算成本高、可复现门槛高**：单任务单次运行平均约 20 小时量级，全部实验在异构集群上完成，未提供精确的硬件配置与归一化计算量，第三方难以复现；论文也承认这不是严格的计算平价比较。
- **LLM 依赖与随机性**：整个搜索依赖专有 API（GPT、DeepSeek）及本地量化模型，生成结果具有随机性和模型版本漂移风险；更换一个小版本骨干可能导致生成分布变化，结论的稳定性有待验证。
- **信息隔离并非绝对安全**：虽然生成器只收到粗略特征计数摘要，但 LLM 预训练数据中可能包含 OpenML 任务与数据集本身的信息（如数据集名称、特征含义、已知最优精度），因此存在潜在的评测集污染风险，论文仅靠粗粒度摘要来缓解，不能完全排除。
- **审计与约束是软性的**：所有限制（scikit-learn 组件、最多 3 个学习器、禁止内部 CV/HPO）都只是提示约束，静态审计只能检测已出现的情况，无法保证所有候选程序都严格合规；一个绕过约束的程序可能在搜索中被用到。
- **精度收益有限**：与 AutoGluon 差异不显著，性能提升主要相对较弱的 auto-sklearn、H2O、XGBoost；与 TabPFN v3 相比仍有小幅落后，说明“代码进化”这一范式尚未在纯精度上占据绝对优势。
- **多样性带来可解释性代价**：生成的程序结构高度自由，某些组件及其交互非常复杂，甚至超过手工 AutoML 流水线的可解释性；论文没有系统评估这些程序的代码质量、可维护性或可迁移性。
- **单一任务类型限制**：仅覆盖表格二分类/多分类，未涉及回归、时间序列、生存分析等，也没有与 LLM 相关的最新无训练方法（如直接提示式推理或更大基础模型）对比。

## 8. 论文的可复现性与伪代码可用性

- **可复现性**：
  - 论文未发布完整源代码仓库链接、提示词模板、候选程序数据或模型权重；仅给出伪代码（Algorithm 1）和文字描述；
  - 实验依赖闭源 LLM API（GPT、DeepSeek）和特定版本（Qwen3-Coder-Next），无法在零成本下复现；
  - 数据集（OpenML）和评估协议（十折划分）完全公开，这一点可复现；
  - 论文提供了较详细的时间预算分配、任务重/普通判定规则、超时与失败处理细节，但缺少候选程序输出示例和完整日志。
- **伪代码可用性**：
  - 主进化伪代码（Algorithm 1）清晰描述了种群大小、变异过程、精英选择与预算循环，适合作为实现参考；
  - 但缺乏关键的 LLM 提示词细节、错误反馈格式化方式、变异指令的具体采样分布、初始种群种子如何生成等实现级信息，仅靠伪代码难以复现完全一致的系统。

  - auto-sklearn（Feurer et al.）、AutoGluon（Erickson et al.）、H2O AutoML，代表传统组合搜索路线；

- **LLM 交叉算子与代码生成进化**：论文引用了一批将 LLM 用作变异/交叉算子进行程序合成与进化搜索的工作（如 EvoPrompt、FunSearch、LLM-GE 等），将 LACE 定位为首次将该思想扩展到完整 AutoML 流水线程序搜索。
- **OpenML 基准与评估实践**：使用 `amlb-classification-all` 套件，与 AutoML 社区广泛使用的 benchmark 协议保持一致，便于与已有结果对比。

## 10. 其他关键内容（可推断的数据/细节）

- **任务规模与硬任务分布**：20 个重任务被特别处理（4 小时超时），最大任务 489 万样本；重任务通常对应高样本或高维场景，候选程序更容易超时或爆内存，这解释了 Qwen3 的较低有效率。
- **无效候选类型**：语法错误、导入错误、运行时异常（如维度不匹配、内存不足、死循环）以及超时四类；失败反馈被回传给 LLM 以便修正，说明“从错误中学习”是进化有效性的重要来源。
- **进化轨迹特征**：初始候选表现通常较弱（零样本对比中最终程序优于首个程序的中位提升约 3 个百分点），且早期代改进速度较快、后期趋缓，符合典型进化搜索模式。
- **与 AutoGluon 的对比细节**：中位精度差为 −0.001（几乎持平），但 LACE 胜出的任务更多集中于高维或非标准化特征分布任务，而 AutoGluon 更擅长资源受限的中等规模任务。
- **审计结果**：仅极少数最终程序（约 0.5% 级别）被发现轻微违反提示约束（如使用 4 个学习器），人工复核后确认不存在恶意或危险代码；但论文未排除搜索过程中存在暂时性违规候选。

## 11. 总结评价

LACE 的核心贡献是概念性的：它把 AutoML 从“搜索超参数与组件组合”重构为“进化可执行程序”，借助 LLM 的代码生成能力打开了一个由 Python 代码自由定义搜索空间的窗口。实验设计在协议公平性、覆盖面、消融与审计方面都相当扎实，主结果（与 AutoGluon 持平、超过较弱传统方法、覆盖优于基础模型）支持其范式可行性。但论文的精度提升幅度有限、计算开销极高、复现门槛大、信息隔离仍存在污染风险，这使得 LACE 更适合被视为一个重要的可行性论证与思想推动，而非立即可落地的实用 AutoML 替代方案。后续工作若能开源全部提示词与日志、引入更严格的评测隔离（如排除公开基准）、并降低 LLM 调用成本，将显著增强该范式的说服力。
