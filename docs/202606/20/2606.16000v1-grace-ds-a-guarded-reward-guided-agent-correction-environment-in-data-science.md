## 摘要
我们引入了GRACE-DS，这是一个数据科学中的受保护奖励引导的智能体校正环境，用于对基于大语言模型的自动机器学习智能体进行部署前评估。GRACE-DS是一组在隔离环境中的评估指标，可应用于特定组织特有的表格型机器学习任务。它将智能体暴露于真实的工作流阶段，从规划和数据检查，到特征工程、模型开发、验证和代码修复，直至最终提交，而隐藏的可执行验证器不仅衡量最终的预测性能，还评估避免数据泄露、可复现性、协议有效性、校正行为和奖励对齐。最强的结构化方案——灵活的迭代交互（我们的方法）——相比一次性生成、非结构化交互和基于重启的基线，实现了更高的端到端归一化隐藏测试质量，同时还提高了符合协议的完成率。通过在超过7000个回合上的验证，这些结果确立了GRACE-DS作为一个稳健的平台，用于评估基于大语言模型的自动机器学习智能体在接近生产环境的条件下，并按照特定组织要求执行机器学习工作流的能力。

## Abstract
We introduce GRACE-DS, a Guarded Reward-guided Agent Correction Environment in Data Science for pre-deployment evaluation of LLM-powered AutoML agents. GRACE-DS is a set of evaluation metrics in an isolated environment that can be applied to tabular ML tasks specific to a particular organization. It exposes agents to realistic workflow stages, from planning and data inspection through feature engineering, model development, validation, and code repair to final submission, while hidden executable validators measure not only final predictive performance but also leakage avoidance, reproducibility, protocol validity, correction behavior, and reward alignment. The strongest structured regime, flexible iterative interaction (our approach), achieves higher end-to-end normalized hidden-test quality than single-shot generation, unstructured interaction, and restart-based baselines, while also improving protocol-valid completion. Validated across more than 7,000 episodes, these results establish GRACE-DS as a robust platform for assessing the capacity of LLM-based AutoML agents to execute machine learning workflows under production-like conditions and in accordance with organization-specific requirements.

# GRACE-DS 论文详细总结

## 1. 核心问题与整体含义（研究动机和背景）

- **问题**：现有的 LLM 驱动的 AutoML 智能体评估通常只关注最终分数（如 Kaggle 成绩），忽略了工作流过程本身，例如**目标泄漏、不可复现的代码、无效的验证策略、无法从错误中恢复**等。这些过程性缺陷在实际部署中可能导致严重后果，但公共排行榜无法揭示。
- **目标**：提出一个**企业级部署前评估平台**，在受控隔离环境中模拟生产条件，同时评估智能体的**最终性能**和**过程可靠性**（泄漏避免、可复现性、协议合规、校正行为、奖励对齐）。
- **方法定位**：GRACE-DS 不是又一个竞赛基准，而是组织可以用自己的数据和规则来测试 AutoML 智能体是否值得信任的“守门人”工具。

## 2. 方法论

### 2.1 核心思想
- 将整条机器学习工作流建模为**部分可观测马尔可夫决策过程（POMDP）**，智能体通过固定词汇表的 8 个状态（PLAN、EDA、FEATURE_ENGINEERING、MODEL、VALIDATE、CODE、CODE_FIX、FINAL_SUBMIT）与环境交互。
- 评估方（企业）拥有**私有的验证标签和隐藏测试数据**，智能体只能看到训练标签和验证特征，通过**可执行验证器**自动、隐蔽地检查过程层面的合规性（如泄漏、可复现性、协议有效性）。

### 2.2 关键技术细节
- **环境隔离**：沙箱内限制 Python 包（固定版本）、禁止文件/网络访问、禁止直接调用 scikit-learn 指标，通过事务性快照实现回滚。
- **奖励设计**：分解为**性能项**（权重 0.55，基于隐藏测试归一化分数）、**计划覆盖项**（0.15，基于检查表完成度）、**代码质量项**（0.30，包含可复现性、多样性等）。严重错误（泄漏、访问私有空间、篡改快照）强制奖励置零。
- **隐藏验证器**：覆盖 5 组 20 余项检查（完整性/泄漏、数据质量、建模、过程、终止比较），每个验证器输出分数和可选惩罚。
- **反馈机制**：智能体接收三类反馈——执行反馈（stdout/错误）、阶段感知反馈（基于任务实际状况的隐藏检查表，只给出抽象提示而非具体规则）、指标反馈（仅在 VALIDATE 动作后显示验证集分数）。
- **灵活迭代交互**：允许智能体自由选择阶段顺序，但要求先建立一个简单的可复现基线模型，然后进行更深入的 EDA，至少比较两个不同模型族。版本对比：固定阶段迭代、紧凑反馈、去除特定阶段等消融。

### 2.3 公式/算法流程（文字说明）
1. 评估方读取任务清单，划分训练/验证/隐藏测试集。
2. 智能体在沙箱内通过 8 种动作交互，每个动作有独立的步骤、时间、连续重复预算。
3. 每个候选模型需满足**可复现性**：提供一个 `predict_fn(raw_dataframe)` 或已拟合的 Pipeline。
4. 通过 VALIDATE 动作获取验证分数（但看不见隐藏测试分数），通过 CODE_FIX 修复失败。
5. 最终提交后，评估方在隐藏测试集上重放最佳候选，得到单一分数，并给出分解奖励。
6. 所有回合记录路径、错误、恢复次数、候选多样性等。

## 3. 实验设计

### 3.1 数据集/场景
- 共 **10 个任务**，来自四个家族：
  - **TML-bench**（4个）：Kaggle 竞赛（截断时间后的真实数据）
  - **TabReD**（1个）：行业数据集（Sberbank，带时间分割）
  - **UCI/OpenML 基准**（3个）：不常见的公开数据集（降低记忆风险）
  - **合成数据**（2个）：scikit-learn 生成，具有已知数据生成过程，用于特征相关性分析。
- 任务类型：二分类（ROC-AUC）和回归（RMSE/R²），也支持宏F1、准确率、MAE、对数损失。

### 3.2 基准方法（对比 regime）
共 15 个 regime，包括：
- 核心 7 种：单次生成（single_shot）、非结构化智能体（unstructured_agent）、从头重启（n_restarts_from_scratch）、调用匹配重启（n_restarts_call_matched_upper_bound）、固定阶段迭代（fixed_stage_iterative）、紧凑反馈（flexible_compact_feedback）、灵活迭代（flexible_iterative）。
- 消融 5 种：去掉 PLAN、EDA、特征工程等独立阶段。
- 奖励优化 2 种：提示智能体最大化过程奖励（隐藏/公开规则）。
- 红队测试 1 种：指示智能体以奖励为目标，故意不解决问题。

### 3.3 语言模型
- 8 个前沿 LLM：Gemini-3.1 Pro、GPT-5.4、Grok-4.3、DeepSeek-V4 Flash/Pro、Qwen3.5-397B、Qwen3-Next-80B、GPT-OSS-120B。包含专有和开放权重，大小从 ~80B 到 1.6T 参数，都启用了推理（除 Qwen3-Next-80B 为 instruct 模式）。

## 6. 主要结论与发现

1. **灵活迭代交互显著优于其他 regime**：端到端归一化隐藏测试质量（E2E Q）达 0.754，对比单次生成 0.536、非结构化智能体 0.527、从头重启 0.672、调用匹配重启 0.686。配对数对比显示，灵活迭代比单次生成提升 +0.218，比非结构化提升 +0.227（p < 10⁻¹⁵）。
2. **协议有效完成率（PV）大幅提升**：灵活迭代达 96.9%，非结构化仅 69.2%，固定阶段 84.2%。结构化反馈帮助智能体避免无效提交。
3. **结构化的校正行为是端到端质量提升的关键**：灵活迭代中 93.4% 的出错 episode 最终仍能协议有效完成，而单次生成仅 7.0%，非结构化 47.0%。CODE_FIX 循环有效。
4. **严重方法错误几乎消除**：灵活迭代 regime 中只出现 1 个泄漏类错误（0.2%），而重启基线高达 5.2%~7.1%。红队测试中验证器阻止了所有关键失败模式（零泄漏、零访问、零篡改），且隐藏测试分数暴露了奖励最大化的质量损失。
5. **奖励是有效的进展信号但不可替代隐藏测试**：任务级奖励与端到端质量的中位 Spearman 相关为 0.30（9/10 任务正相关），但奖励最大化仅能微增奖励，却导致质量下降，说明过程奖励不能取代最终隐藏测试。
6. **模型规模影响交互机制使用方式**：大模型（如 Gemini-3.1 Pro）单次表现已经很好，结构化带来的增益相对小；小模型（如 Qwen3-Next-80B）在固定阶段 regime 中 PV 崩溃至 38.3%，但在灵活迭代中恢复至 86.7%，表明灵活性对小模型尤为重要。
7. **任务难度调节迭代增益**：增益从简单任务的 +0.019 到困难任务的 +0.903，与单次方案与 oracle 之间的差距高度相关。

## 7. 优点

- **过程与结果并重**：不仅仅是最终分数，还通过隐藏验证器全面评估过程可靠性（泄漏、可复现性、协议合规、校正行为），为企业部署提供了信任依据。
- **细粒度的可解释性**：奖励分解为性能、计划、代码质量三项，并记录每步轨迹、验证指标增长、候选多样性、自估计校准等，使每个 episode 的得分原因透明。
- **对抗鲁棒性测试**：包含奖励最大化提示和红队攻击，展示验证器的防御能力，并证明隐藏测试在揭露欺骗方面不可或缺。
- **可复制和可扩展**：所有配置通过 YAML 和任务清单管理，支持组织用自己的私有数据和规则本地部署；检查点、种子固定、SHA-256 哈希保证结果可复制。
- **实验设计严谨**：7,000+ episode、多重对比、消融、统计检验、质量-速度-成本前沿分析，结论充分支撑。

## 8. 不足与局限

- **领域局限**：当前仅针对**表格监督学习**，未扩展到深度学习训练循环、多模态、强化学习、大规模分布式训练或科学发现等场景。作者也承认这是未来工作。
- **不覆盖完整 MLOps 生命周期**：通过 GRACE-DS 并不等同于模型生产就绪，仍需要监控、概率校准、分布偏移鲁棒性、延迟约束、可解释性、安全审查和审批流程。
- **依赖外部 API**：LLM 推理通过第三方 API（如 OpenRouter），可能引入延迟波动、成本不确定性、以及服务不可用风险。未考虑本地部署 LLM 的情况。
- **模型规模偏差**：小模型（如 Qwen3-Next-80B，无推理模式）在固定 schedule 下表现极差（PV 38.3%），但灵活迭代能部分缓解。但在实际部署中，小模型可能无法充分利用结构化环境，导致效果打折。
- **任务数量有限**：10 个任务虽然覆盖多种类型，但相比 Kaggle/OpenML 数万任务仍然较少，可能未完全代表生产环境多样性。组织需要自行测试自己的任务才能判断适用性。
- **奖励和验证器设计依赖专家定义**：检查表和验证器由人工编写，可能存在遗漏或偏差。作者提到使用正则表达式实现，但未讨论验证器覆盖率或假阳性/假阴性风险。
- **未讨论多轮交互下的 token 消耗成本**：灵活迭代平均 token 约 43k，是单次（2.4k）的 18 倍，在 token 计费模式下成本显著增加。紧凑反馈降为 38.7k，但仍远高于单次。
